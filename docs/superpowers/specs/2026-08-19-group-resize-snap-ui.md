# 分组框缩放：把手 UI + 缩放时的边缘对齐

日期：2026-08-19
状态：已批准（2026-08-19 Nick 拍板三条：把手只给四角；缩放只吸其它卡与框的边 + 10px 网格；缩放下限 = 刚好完整包住成员卡）
前置：`2026-08-05-canvas-groups`（框的缩放手势与最小尺寸）、`2026-08-04-canvas-align-guides`（四线对齐的纯几何与七条约束）、`2026-08-12-canvas-ux-refinements`（去中线 / 阈值按屏幕像素 / Alt 临时绕过）、`2026-08-19-group-frame-align-snap`（拖动时的框对齐；本 spec 接管它「明确不做」里的缩放那一条）、`2026-08-19-group-card-selection-polish`（框的选中态视觉）

## 目的

Nick 两句：**接下来做缩放的对齐**，另外**分组框需要增加缩放交互的 UI**。

今天框的八个缩放把手是**完全不可见**的 10px 命中区（`data-group-resize`，只给了 cursor），用户不碰上去根本不知道框能缩放；而缩放全程也不吸附 —— 拖动刚在上一回合接上了对齐，缩放还停在像素级自由。

追加一条（Nick 同回合补的）：**框调整大小时不能小过内部卡片**，避免内部卡片脱离分组。这是**硬夹取**而不是吸附（见决策 3.5），与他否掉的「吸到成员包围盒」（软吸附）不矛盾：软吸附会在「我就是想把这张卡挤出去」时黏住手，硬下限则是把「缩放不该造成退组」这件事从手感问题升级成不可能事件。

## 决策

### 决策 1：把手视觉**只给四角**，选中时显示（Nick 拍板）

- 四角各一段**离框边一段距离的弧**（Nick 2026-08-19 两轮敲定，取代最初定的 6px 方块）：16px 见方、只画相邻两条边的 **2px** 品牌橙，圆角与框体**同心** —— 框体 `rounded-[16px]`、把手**内缩 8px** ⟹ 弧的曲率 **8px**（16 − 8）。
  - 第一版是「贴着圆角画 1.5px 的弧」，实机上与框体那圈 24% 描边糊在一起、根本不明显 ⟹ 往里挪 + 加粗。方块那版则是压在 16px 圆角上露出「直角贴曲边」的破口。
  - **角的命中区随之扩到 24px**（内缩 8 + 弧 16 = 弧的外沿）：只留 10px 的话弧的大半截落在命中区外，看得见抓不着比不画更糟。边中点仍是 10px（无视觉，不必扩）。代价：角上 24×24 不再是「拖整组」的把手，框最小 120×80 时横向仍剩 72px 可拖。
  - 弧是 `pointer-events-none` 的纯绘制，指针归命中区。
  - 四个数（框体圆角 / 内缩 / 曲率 / 角命中区）耦合：Tailwind 的 arbitrary value 读不到 JS 常量，只能靠 `HANDLES` 上方那段注释 + 单测把它们钉在一起。
- **命中区仍是八个**：四边中点的把手照旧能拖，只是不画视觉。命中区与视觉解耦，几何一行不改（把手仍是 10px，比 6px 的视觉大一圈，符合「视觉小、热区大」）。
- **只在选中时出现**，hover 不浮现：可发现性由「点一下框就出现把手」承担；一屏多个框时不冒出几十个小方块。
- 与选中态的其它元素不冲突：`.node-beam` 在框体那层（`inset:-1.5px`），把手在节点层、`zIndex` 更高，四角处把手压在光束上是预期的。

### 决策 2：缩放吸附与拖动**同一口径**（Nick 拍板）

- 只吸**被拖的那条边**（角把手 = 两条边，两轴各判一次）到画布上其它卡与框的四条边缘；对边不动。
- 阈值 `SNAP_THRESHOLD_PX / zoom`、四线口径（无中线）、对齐总闸与 Alt 临时绕过**全部沿用**，不新造判据。
- 命中对齐线优先；未命中则该边落 **10px 网格**（`SNAP_GRID`）—— 拖动今天就是这个层级顺序（RF 做网格、我们做边缘），缩放此前两样都没有。
- **不吸自己的成员**：与拖动同一条依据（框会吸在自己的内容上）。也**不吸成员的整体包围盒**（Nick 否掉：几何是真相，把成员挤出框就是退组，不该被黏住）。
- 缩放期照旧**不平移成员**（几何变化可能把成员挤出去，那是容器模型的既定语义）；落库与归属复判仍走 `updateGroupGeometry`，一行不改。

### 决策 3：最小尺寸夹取**赢过**吸附

顺序：原始位移 → **夹位移**（保住「西/北方向拖过最小尺寸时框不整体滑走」这条已修过的坑）→ 得候选矩形 → 吸附被拖的边 → **再夹一次最小尺寸**（吸附可能把边推过最小值）。夹取是硬约束，吸附是建议。

### 决策 3.5：缩放的**硬下限 = 刚好完整包住成员卡**（Nick 拍板）

- 下限盒 = **重新建框会得到的那个几何**：`boundingBoxOf(成员, GROUP_PADDING)` —— 成员卡包围盒（按 `cardSize(kind)` 取各类型真实尺寸，audio 宽 210，一律按 `CARD_W` 会把它切掉）+ 四周 **24px 内边距**（四边等宽）。
  - **2026-08-20 修正**：原文这里还有「+ 顶部再让出 `GROUP_TITLE_H`」，那是标题条还在框内那会儿的设计残留 —— 标题条实际渲染在框**外**（`-top-8`），框内让出的 32px 谁都不用，表现为上边距恒比另三边宽一截且收不掉。该常量已删，见 plan `2026-08-20-group-frame-top-padding`。
  - **Nick 2026-08-19 第二轮改口**：第一版取「四周 0 间隙」，实机后改成与建框同一份内边距，于是「框收到最紧」≡「把这批卡重新圈一次」。实现上直接委托 `boundingBoxOf`，不自己再算一遍 padding —— 口径一份，连它 floor/ceil 的取整方向（保证整数框恒包含浮点框）也一并继承。
  - **直接后果（不是 bug，有单测钉着）**：刚建出来的框一点也收不动，只能往外放 —— 它本身就等于这个下限。
- 逐边夹取：四条边分别不得越过下限盒的对应边。
- 与 `MIN_GROUP_W/H` **取较大者**：空框仍受最小尺寸约束；有成员时下限由成员决定。
- **存量数据的成员已经露在框外**时：下限按成员**实际**包围盒算 ⟹ 框不能再往里收，但**不强行把框撑大**（那会在用户没动手的情况下改几何）。
- 为什么是硬夹取而不是「吸附 + 提示」：`groupHitFor` 按中心点判定归属，缩放把卡挤出去就是**静默退组**（`updateGroupGeometry` 会重算谁被挤出去，那一步是正确的，只是用户并不想要）。让它不可能发生比让它可撤销更省事。

### 决策 4：辅助线通道统一收进 store（**修正 `2026-08-04` 约束 7**）

约束 7 原文是「辅助线是纯瞬态，留组件本地不进 store」。缩放手势在 `GroupNode` 里（自己的 window 监听，不经 RF 拖拽链），而辅助线层挂在 `AssetCanvas` 的局部 state 上 —— 两处不通。

修正：**辅助线改走 store 的瞬态字段**（`UIState.alignGuides`，不进 persist），拖动与缩放两个来源写同一个字段，`AlignGuides` 层订阅它。

- 「纯瞬态」那一半仍然成立（不落盘）；作废的只是「不进 store」。
- 跨组件协调走 store 字段是本项目的既定范式（`renameTarget` / `genForm` / `addMenu` 皆然），不为此另造事件总线或 ref 传递。
- 性能上更好而不是更差：今天 `setGuides` 是 `AssetCanvas` 自己的 state，每帧变化会重渲 `AssetCanvas` 连带 `ReactFlow`；改成 store 后**只有辅助线层订阅**，拖拽期不再牵连整块画布。
- 两条来源共用一个字段（而不是各给一个）：否则就是两套并存的机制，迟早画出两套观感不同的线。

### 决策 5：候选集取数收成一份纯函数

`AssetCanvas.snapshotCandidates` 与缩放这条新路径都要「视口内的卡与框，排掉若干 id」。抽 `candidateRects(nodes, viewport, size, exclude)` 到 `align-guides.ts`，两个调用点共用。`GroupNode` 侧的 nodes / 视口 / 容器尺寸从 RF 的 store 取（`s.width` / `s.height` / `s.transform` 都在里面），不新增 prop、不往 `node.data` 里塞函数。

## 约束

- 纯几何仍下沉 `src/lib/align-guides.ts`（无副作用、不认识 RF），新增 `snapResizeEdges` 与 `candidateRects` 均单测覆盖；`GroupNode` 只接线。
- 不引入新令牌 / 新动效 / 新 keyframes；把手用既有色与既有圆角档。
- 框的落库路径（`updateGroupGeometry` 逐个 `updateCanvasGroup`）、成员归属复判、撤销条目形状**一律不变**。
- 命中区几何（8 个 10px）不变 —— 改的是「画不画」，不是「能不能拖」。

## 明确不做

- **键盘缩放**：把手是纯鼠标 affordance，读屏用户得不到任何东西，故把手 `aria-hidden`，不假装可用。键盘调框尺寸是已知缺口（承接 `2026-08-13-group-a11y-and-menu-debts` 的口径），单独立项。
- **缩放期显示 w×h 读数气泡**：未被要求，且要新造一层浮层。
- **等比缩放（按住 ⇧）**：与吸附叠在一起要先定「谁赢」，另开。
- **软吸附到成员包围盒**（Nick 否掉，见决策 2）—— 注意这与决策 3.5 的**硬下限**是两件事：不吸，但不许越过。
- **拖动那条链的任何行为变化**：本回合只把它的辅助线出口换成 store，落点 / 吸附结果一模一样。

## 成功标准

1. 选中框 → 四角出现**贴着圆角的弧**（不是方块）；未选中不显示；命中区仍是 8 个（边上照旧能拖）。
2. 拖某条边靠近另一张卡 / 另一个框的同名或异名边缘 → 出辅助线并吸附；对边不动。
3. 未命中对齐线时该边落 10px 网格。
4. 拖过最小尺寸：框停住而**不整体滑走**（既有坑的回归锁仍绿），吸附不能把边推到最小值以内。
5. 关掉对齐开关 / 按住 Alt：缩放不吸（与拖动同一判据）。
6. 缩放不吸自己的成员。
7. **把任一条边往里拖到「成员包围盒 + 24px 内边距」时，框停住**：成员一张都不会因缩放而退组（单测锁逐边夹取 + 「audio 卡按 210 宽算」+ 「刚建的框收不动」三条口径）。
8. 空框（无成员）仍只受 `MIN_GROUP_W/H` 约束。
9. 拖动的对齐行为与上一回合完全一致（辅助线换通道后无回归）。
10. `pnpm lint` / `tsc --noEmit` / `pnpm test` / `pnpm test:tz` 全绿。
