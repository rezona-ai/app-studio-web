# 撤销删框缺成员坐标（删框 → 整理 → 撤销，卡片回不到框里）

- 日期：2026-08-18
- 范围：`src/store/actions.ts` · `src/store/pending-delete.ts`（`PendingGroupDelete` 形状）
- 相关既有稿：`2026-08-05-canvas-groups`（分组框 / 删框延迟删除）· `2026-08-03-canvas-undo`（撤销栈总纲）· `2026-08-17-tidy-groups-as-boxes`（框作为整体参与整理）· `2026-08-18-group-undo-gaps`（同源症状的上一轮）

## 1. 问题与根因

用户报告：**删掉分组框 → 点一键整理 → 点 Toast 上的「撤销」，框回来了，但框里的卡片没回到原位**——画布上留下一个标着「Group · 2 card(s)」的空框，那两张卡混在整理后的货架顶行里。

复现（失败用例的实际输出）：

```
groups    [{"id":"g1","x":2000,"y":2000,"w":400,"h":300}]
after     m1:{240,0}  m2:{480,0}
groupIds  m1→g1  m2→g1
```

根因是三段既有逻辑叠在一起，各自都对：

1. `deleteGroup` 走延迟删除，本地只摘框 + 清成员 `groupId`，`PendingGroupDelete` 快照里只有 `group` 与 `memberIds`，**没有成员坐标**。
2. 此刻原成员成了自由卡，`tidyCanvas` 把它们当散卡重排（框已不在 `groups` 里，压根不进整理输入）。
3. Toast 的「撤销」是 **token 路径**（`undo(token)`，刻意越过栈顶只撤那一条删框，见 `undo()` 注释）；`cancelPendingGroupDelete` 依「服务端框与成员 `group_id` 全程没动过，故不回写」的前提，只放回框几何 + 归属，**不碰坐标**。

于是框按快照回到旧坐标、成员按整理后的坐标停在别处 —— 又一次「几何是真相 vs 归属投影」当场打架，与 `2026-08-18-group-undo-gaps` 同源；只是这次缺的不是撤销栈的格子，而是**延迟删除快照里缺了成员坐标**。

⌘Z 栈路径不受影响：栈序是先撤整理再撤删框，两步下来自洽。只有 token 这条乱序撤销会坏，而它正是 Toast 按钮唯一的入口。

## 2. 目的与成功标准

目的：让「撤销删框」恒等于**回到删框那一刻**——框、成员归属、成员坐标三者一起回滚，且服务端与本地一致。

成功标准（均为可断言用例）：

1. 删框 → 整理 → `undo(token)`：框回旧坐标、成员 `groupId` 全回来、**成员坐标回到删框前**，成员仍落在框的几何范围内。
2. 同上路径：坐标真的变过的成员走一次批量回写（`batchUpdateCanvasItems`）——整理已把新坐标落库，不回写则刷新后又散开。
3. 窗口内没有任何东西挪过成员（删框后直接撤销）：**不发**坐标回写请求，撤销仍把框与归属放回（既有用例不回归）。
4. 空框删除后撤销：不抛、不发回写。
5. 窗口内某成员卡被删掉：撤销跳过它，其余卡照常回位，不因幽灵 id 发请求。
6. ⌘Z 栈路径（撤整理 → 撤删框）行为不变：第二步时快照与当前坐标已一致 ⟹ 无变位、不重复回写。

## 3. 决策

**决策 1：`PendingGroupDelete` 增记成员坐标快照，撤销时一并放回。**
快照形状从 `memberIds: string[]` 升为 `members: { id: string; position: { x: number; y: number } }[]`（`groupId` 无需记：删框前它们**必然**属于这个框，就是 `group.id`）。
选它而非「整理前先冲刷待删框」或「撤销时按成员当前位置重新落框」：
- 与**撤销删卡**完全同构 —— 那条放回的就是删除那一刻的卡对象（含 `position`），撤销删框放回删除那一刻的框 + 成员是同一语义，不引入第二套心智。
- 覆盖窗口内**任何**挪过原成员的操作（整理 / 拖卡 / 拖框），而不只是整理这一条路径。
- 「按当前位置重新落框」会让框吞掉整理后与成员混排的别人家卡片，且与「框几何归用户所有」冲突。

**决策 2：坐标回写只发给真的变位的卡，走既有 `persistAssetPositions` 批量通道。**
逐卡比对快照与当前坐标，变位集合为空则一个请求都不发（标准 3/6）。不新开通道：与整理 / 拖拽 / 撤销位移同一条批量端点，失败文案与限流都已在内。

**决策 3：归属仍不回写（既有前提不变）。**
删框窗口内服务端的框与成员 `group_id` 从没动过，故只有坐标需要补写；乐观期建的框那条例外（`groupIdAlias` 判据）沿用现状。

**决策 4：本地一次 `set` 落定框 + 归属 + 坐标。**
分两次会闪一帧「框回来了但卡还在外面」——正是这次要修的那个画面。

## 4. 约束

- 撤销栈**存数据不存闭包**；`pendingGroupDeletes` 仍在 actions 闭包里（含定时器，不可序列化）。
- `pid` 二次校验沿用（`cancelPendingGroupDelete` 现有那道）。
- 不做 redo。
- 框的 `w/h` 只读，本轮一律不碰。

## 5. 已知限制（本轮不做，Minor）

- **窗口内被拖进别的框的原成员**：撤销删框仍会无条件把它抢回旧框（`cancelPendingGroupDelete` 无条件按快照写归属），与 `undoCreateGroup` 评审 M2 修过的那条同源，但可达路径更窄（要在 6s 窗口内完成拖入另一个框）。本轮只补坐标，不扩到归属仲裁。
  ⚠️ 本轮的坐标回写会让这个分歧**跨刷新存活**（评审 M1）：拖入框 B 那次 `persistAssetPositions` 带 `groupChanges` 把 `group_id=B` 写进了服务端，而撤销只发坐标（不带 `groupChanges`）⟹ 刷新后这张卡几何上落在旧框 A 里、服务端归属却是 B。下一轮要收口的话，判据应与 `undoCreateGroup` 的逐卡仲裁合成一份。
- **窗口内成员卡被删 / 占位卡被真实卡替换**（评审 M2/M4）：前者撤销删框时跳过它（符合标准 5），但随后再撤销删卡会把它当自由卡放回，而服务端 `group_id` 仍是旧框；后者快照记的是 `pending_` id，撤销时对不上、该卡不回框。两条都是 `memberIds` 时代就有的边界，本轮未变差。
- **并发写序**（评审 M3）：`positionInFlight` 只做同坐标合并、不按 item 串行化。整理那批若走 `retryAsync` 退避重发，可能晚于撤销的回写落地，服务端最终留下整理后的坐标（本轮症状的窄变体）。与 `undo()` 的 `positions` 分支同款既有风险，非本轮引入；要收口可参照框那边的 `pendingGroupTail` 串行队列。
- **删卡 → 整理 → 撤销删卡**：卡按原坐标放回，可能与整理后的货架重叠。那是「卡回到了它自己的原位」，不构成归属与几何打架，不在本轮范围。

**已采纳并修复：**

- **I1（Important）· `⌘Z 栈路径` 用例是空断言**：它绿不是因为「第二步无变位」，而是被 `persistAssetPositions` 的同坐标合并挡下的 —— 第一次 `undo()`（撤整理）刚写过同一批同坐标，`finally` 里的在飞标记（`positionInFlight`）还没清，第二次 `undo()` 同步发起就被判「已在飞」而丢弃。实测：把变位判据放宽成 `return pos != null`（无条件回写全体成员），该用例**仍绿**。修法：第二次 `undo()` 前加一个宏任务 tick 让标记清干净；同一变异随即转红（`expected "vi.fn()" to not be called at all, but actually been called 1 times`），真实现仍绿。探针结论写进用例注释。
