# 列表与手感的四条修补：让眼睛跟得上手

> 状态：设计稿 · 2026-08-08
> 分支：`fix/canvas-list-and-feel`（P2 第二批 / 共三批）
> 来源：2026-08-07 对 179 个未推送提交的全量评审，四条**均已逐条对着代码重新核实**
> 前置：P0 四回合、P2 第一批（撤销与浮层）、P2 第三批（钱与可见性）均已合并

## 目的

前两批修的是「系统骗人」和「失败没人告诉你」。这批修的是**操作完之后，眼睛找不到东西**：

- 在画布上点了一张卡，右侧列表纹丝不动，得自己滚去找；
- 想在列表里选连续一段，只能一个个 ⌘ 点；
- 刚点下生成，那张转圈的卡**跑到列表最底下**去了；
- 一次拖进 5 个文件，5 张卡叠在同一个坐标上，像只上传了一个。

四条的共性是：**功能都在，但把用户的注意力甩掉了**。每条都只需小改。

### 缺陷 1 · 画布选中后，列表不滚动到对应行

`src/components/canvas/` 全目录 **无 `scrollIntoView`**（已 grep 确认）。
反向是通的：列表行点击会 `ensureVisible(asset.position)` 把画布滚过去（`AssetListDrawer.tsx:72`）——
所以「列表 → 画布」有，「画布 → 列表」没有。

后果：列表开着时在画布上点一张卡（或用方向键、搜索跳转换选中），列表高亮了某一行，
但那行可能在滚动区外，用户完全看不到反馈。资产一多，列表就退化成一个只能从上往下翻的静态清单。

### 缺陷 2 · 列表无 Shift 范围多选

`AssetListDrawer.tsx:67` 只判 `e.metaKey || e.ctrlKey`（切换单条），没有 `shiftKey` 分支。

后果：想选「第 3 到第 12 行」只能 ⌘ 点十次。而这正是列表相对画布的**核心优势场景**——
画布上框选受布局摆布，列表是线性的、天然适合区间操作。

### 缺陷 3 · 刚生成的卡沉到列表最底

`src/lib/asset-list.ts:22` 的注释写着：

> 缺 seq 的历史资产(本次改动前落库的)恒排最后

**这个人群不存在。** `map.ts:106` 是无条件 `seq: it.id`，而 `CanvasItemData.id` 是
`number` 类型的**数据库自增主键**（`pgc/types.ts:27`）—— 服务端回来的每一条都有 seq。

真正 `seq == null` 的只有**前端刚建的 `pending_` 占位卡**。而默认排序是
`{ by: 'seq', desc: true }`（最新在前，`store/index.ts:313`），于是：
**用户点下生成，那张转圈的占位卡直接沉到列表最底** —— 恰好与「最新在前」相反。

更糟的是 `sortAssets` 里那段「无 seq 的沉底**不随升降序翻转**」（`asset-list.ts:43-46`），
让占位卡在两个方向下都在最底，怎么切都找不到。

### 缺陷 4 · 多文件拖放，坐标完全重叠

`AssetCanvas.tsx:936-938`：

```ts
// 落在松手处(约束 1);多文件由 uploadAsset 内的 avoidOverlap 级联避让
for (const f of accepted) void useStore.getState().uploadAsset(f, { spawnAt });
```

**那句注释是错的。** 每个文件是**独立一次** `uploadAsset` 调用 ⟹ 各自 `count=1`、
循环里 `i === 0`，而 `addGenPlaceholders` 的判据是（`actions.ts:566`）：

```ts
const position = (opts?.spawnAt || opts?.pinAt) && i === 0 ? target : avoidOverlap(...);
```

带 `spawnAt` 且 `i===0` ⟹ **跳过避让，直接落在 `target`**。N 个文件、N 次调用、每次都是首张，
于是 N 张卡坐标一模一样，用户看到的是「只上传了一个」。

⚠️ 注意成因**只有这一条**：不是「`avoidOverlap` 跨调用不生效」。`occupiedBoxes`（`actions.ts:503`）
读的是**整个 store**，避让只要被调用、跨调用就有效（粘贴多文件不传 `spawnAt`，正是靠它自然铺开）。
问题在于带 `spawnAt` 的首张**压根没走到**避让那一步。原注释把「批内 / 跨批」当成了病因，是误判。

## 约束

1. **不改既有 UI 种类**：不新建按钮 / toast / 动画，复用既有令牌与基础组件（CLAUDE.md「UI/UX 范式」）。
2. **不动 `addGenPlaceholders` 那条判据**：`(spawnAt||pinAt) && i===0` 被双击生成、重试落回原位
   等多条路径依赖，改它会波及本轮之外的行为。缺陷 4 在**调用方**解决。
3. **降低动态要照顾**：新增的滚动行为必须在 `prefers-reduced-motion: reduce` 下退化为瞬时跳转。
4. **每条独立可测、独立可评审**：四条各自一个提交，互不依赖。
5. **纯逻辑下沉**：排序与区间计算是纯函数，放 `lib/` 并单测，不塞进组件（CLAUDE.md 开发范式）。

## 方案

### 1. 选中变化时把对应行滚进视野（缺陷 1）

在 `AssetListDrawer` 里对 `selectedIds` 的**末位**（最后被选中的那个）滚动：
行挂 ref，`useEffect` 里 `scrollIntoView({ block: 'nearest' })`。

`block: 'nearest'` 而非 `'center'`：已经在视野里的行**不动**，避免每次点选都让列表跳一下。

**必须跳过「本次变化由列表点击自己触发」的情形**：否则点第 3 行 → 触发滚动 → 与用户的滚动位置打架。
用 ref 记一个「本次 setSelection 来自列表」的标记，effect 里见到就跳过并清掉。

⚠️ 约束 3：`scrollIntoView` 的 `behavior` 走 CSS 而非 JS 参数 —— 容器加
`motion-safe:scroll-smooth`，reduce 下自动退化为瞬时。不新增 keyframes。

### 2. Shift 范围多选（缺陷 2）

`AssetListDrawer.tsx` 的 `onClick` 加 `shiftKey` 分支：

- 用 ref 存**锚点**（上一次非 Shift 点击的行 id）；
- Shift 点击时，在**当前已排序 / 已过滤的 `rows`** 上取锚点到本行的闭区间，整段选中。

在 `rows` 上取区间而非在 `assets` 上：用户看到的是什么顺序，选中的就该是哪一段。
排序或过滤变了，区间语义随之变化，这是对的。

区间计算下沉为 `lib/asset-list.ts` 的纯函数 `rangeBetween(rows, anchorId, targetId)`，单测覆盖
（锚点在后、锚点已被过滤掉、锚点等于目标等边界）。

**锚点的三条来源与一处有意的不对称**（评审与终审逐步补全，此处收口）：

1. 列表内**非 Shift** 点击 → 设为该行；Shift 点击**不**设（否则连续 Shift 区间一路漂走）。
2. 选中从**列表之外**变化（画布点选 / 框选 / ⌘A / 右键 / Inspector 跳转 / 撤销恢复）→ 锚点跟随，
   否则 Shift 算出的区间与用户**看到的**选中态脱钩。
3. ⌘+Shift 把区间**并入**现有选区（对齐 Finder / 资源管理器 / VS Code：加一段而非换一段）。

⚠️ **不对称**：外部把选中清空 → 锚点也清（列表没有任何依据）；而在列表里 ⌘ 点掉最后一条
导致选区为空时 → 锚点**保留**在刚点的那一行（用户刚碰过它，它仍是焦点，Finder 同款）。
两条路径有意不同，各有测试钉住。

**已知与惯例的差距**（终审 fin-rewrites 指出，本轮不修）：Finder 等在**设锚那次点击**时快照选区，
每次 ⌘+Shift 算「快照 ∪ 区间」，故连续 ⌘+Shift 能来回伸缩；这里是「当前 ∪ 区间」，**只增不减**
（连点两次 ⌘+Shift 收窄不回来）。仍严格优于改动前的「整个替换」（那会丢掉先前攒的散条目）。

### 3. 无 `seq` 视作 +∞（缺陷 3）

`asset-list.ts` 的 `compareBy` 与 `sortAssets`：把「无 seq 沉底」改成「无 seq 视作最大」，
**并让它正常参与升降序翻转**：

- `desc: true`（最新在前，默认）→ 占位卡在**最前**；
- `desc: false`（最旧在前）→ 占位卡在**最后**。

两个方向都自洽，因为占位卡语义上就是「最新的」。删掉 `sortAssets` 里那段不翻转的特判，
并把 `compareBy` 那句描述不存在人群的注释改准。

**两处附带影响，此处显式认领**（评审 rv-sort 点出，均已补测试钉住）：

- **失败态占位卡也会钉在第一行**（改前钉在最后一行）。`markAssetsFailed` 只改 `status`，
  id 仍是 `pending_`、仍无 seq。这是想要的 —— 刚失败的东西该在眼前，而不是沉到一百行以下
  让用户以为什么都没发生。
- **多张占位卡之间是「先建的在上」**，与整列表「新的在上」方向相反。它们同为 +∞、无从分辨，
  维持插入原序是合理选择；要让这一小段也翻转就得给 +∞ 组特判，而特判正是本条要删掉的东西。
  **已知取舍，不改。**

### 4. 首张 `spawnAt`、其余 `nearAt`（缺陷 4）

> ⚠️ 本节**修订过两次**。初版写「按 index `cascadePosition`」，Nick 据此拍过板；
> 评审 rv-drop 实测推翻了当时的两条依据（见下「初版为什么不够」），Nick 复核后改用 `nearAt`。

`AssetCanvas.tsx` 的 `onDrop`：

```ts
const spawnAt = screenToFlowPosition({ x: e.clientX, y: e.clientY });
const nearAt = spawnAtPoint(spawnAt);   // 中心口径 → 左上角口径,两者不可混用
accepted.forEach((f, i) => void uploadAsset(f, i === 0 ? { spawnAt } : { nearAt }));
```

依据是代码库既有的三口径分工（`actions.ts:63-67` 的注释，非本轮新立）：

| 口径 | 原点 | 精确性 | 避让 | 语义 |
|---|---|---|---|---|
| `pinAt` | 左上角 | 精确 | 否 | 原卡已被丢弃，位置刚空出来 |
| `nearAt` | 左上角 | 起点 | **是** | 原卡还在画布上，新卡该落它旁边；压住它就是骗人 |
| `spawnAt` | **中心** | 精确 | 否 | 用户点哪就落哪，该处已有卡也照落，**不可改** |

只有**第 1 个**文件有用户指定的落点 → `spawnAt`（约束 1 不破）；第 2..N 个**没有任何用户指定点**
→ 正是 `nearAt` 的语义，自动铺开且不埋既有卡。

**已认领的边界**：第 1 张仍会精确落在松手处，那里若已有卡就是压上去 —— 这是 `spawnAt` 写死的
语义（与双击空白处生成同款），不是本条要修的东西。store 层探针实测（松手处已有一张卡，拖 3 个文件）：
`已有卡 110,125 | 新卡 110,125 | 新卡 110,365 | 新卡 110,-115` —— 三张新卡两两不同、后两张自动避开。

#### 初版（`cascadePosition`）为什么不够

1. **「与双击生成多张的观感一致」是假的**。双击多张时 `cascadePosition` 只是 `placeTarget` 的
   **起点**，`addGenPlaceholders` 随后对第 2..N 张跑 `avoidOverlap` 把它们撑开；
   而拖放路径每个文件都是独立一次调用、每张都是 `i===0`，**全程不过避让**。
2. **重叠只减半**。卡片 180×200、`CASCADE_STEP=40` ⟹ 相邻卡仍重叠约 **78%**，
   视觉上是一摞只露 40px 边的牌，「拖进 5 个像只上传了一个」这个原始症状没真正解决。
3. 且**级联不避让既有卡**，会连本来在那儿的卡一起埋掉 —— 这是改动前没有的新代价。

同时把 `AssetCanvas.tsx` 那句注释改准：成因只有「带 `spawnAt` 的首张跳过避让」一条。
**`avoidOverlap` 只要被调用，跨调用是生效的**（`occupiedBoxes` 读的是整个 store，
粘贴多文件不传 `spawnAt` 故恒过避让、自然铺开）—— 问题不在避让的作用域，在于压根没走到它。
（初版注释与 commit message 里那句「`avoidOverlap` 是批内避让、跨调用不生效」是假命题，已更正。）

## 成功标准

1. 列表开着时，在画布上点选一张**当前不在列表可视区**的卡 → 对应行滚进视野；
   已在视野内的行**不触发滚动**（`block:'nearest'` 的效果）。
2. 在列表里点击某一行 → **不**触发自动滚动（避免与用户滚动位置打架）。
3. Shift 点击：先点第 3 行、再 Shift 点第 12 行 → 第 3–12 行全部选中（按当前排序/过滤后的顺序）。
   反向（先点 12 再 Shift 点 3）结果相同。
4. 锚点行已被过滤掉时，Shift 点击**退化为单选**，不报错、不选出诡异区间。
5. 占位卡（`seq == null`）在默认排序（`desc:true`）下排**最前**；切成 `desc:false` 后排**最后**。
6. 有 seq 的资产之间的相对顺序不受本次改动影响（回归）。
7. 一次拖入 3 个**同类**文件 → 3 张占位卡坐标**两两不同**；首张精确落在松手处（`spawnAt`），
   其余走 `nearAt` 并自动避开既有卡。落点须经屏幕→画布变换（不是直接用 `clientX/Y`）。
   ⚠️ **「同类」是必要限定**（终审 fin-branch 实测）：文本文件走 `actions.ts:892-898` 那条
   `await file.text()` 的异步分支、落位晚于同步的图片。若拖放列表里**第一个**恰是 .txt/.md，
   它带的 `spawnAt`（精确、不避让）会在图片已占住松手处之后才落下，于是压在那张图片上。
   仍严格优于改动前（N 张全叠），入口也窄；**列为已认领的边界，本轮不修** ——
   要修得让文本分支也把落位提前到 await 之前，那会动 `uploadAsset` 的结构，超出本轮范围。
8. 单文件拖放的落点与改动前**完全一致**（回归）。
9. `prefers-reduced-motion: reduce` 下滚动为瞬时，无平滑动画。
10. 四道闸门在合并结果上重跑全绿：`pnpm lint` / `pnpm exec tsc --noEmit` / `pnpm test` / `pnpm build`。

## 明确不做

- **不做列表虚拟化**：当前列表已限高 + `scrollbar-auto`，资产量级未到需要虚拟化的程度；
  真要做属独立回合（画布本身已有 `onlyRenderVisibleElements`）。
- **不改 `addGenPlaceholders` 的落位判据**（约束 2）。
- **不动 ⌘A「只选视口内」**：那是工程健康度清单里的独立条目（建议二段式），不在本轮。
- **不加「按时间排序/分组」**：依赖后端 `created_at` 进契约层，属 P1 第 4 项。
- **不碰 P1 四项与工程健康度清单**。
