# 画布拖拽吸附与对齐辅助线

> 状态：设计稿 · 2026-08-04
> 关联：P1 最后一项。已完成：搜索跳转、列表视图（`2026-08-04-canvas-list-view.md`）、批量操作（`2026-08-04-canvas-bulk-actions.md`）。
> 同期未做：P1 的「框 / 分组」（等后端加字段，届时另立项）。

## 目的

**手动摆卡片全靠肉眼，摆不齐。**

现状（本次动工前实测）：

- `SNAP_GRID = 10` 只被 `tidyLayout` 的输出用（`card-layout.ts:351`），**拖拽完全没有吸附**——鼠标松在哪就是哪，坐标带任意小数。
- ReactFlow 的 `snapToGrid` / `snapGrid` 两个 prop 一个都没开（`AssetCanvas.tsx:729-800`）。
- `onNodeDrag`（拖拽进行中）没有接，只接了 `onNodeDragStart` / `onNodeDragStop`。

于是「一键整理」（tidy）能排得整整齐齐，用户手一动就再也回不去那个精度——想把新生成的卡插进已有一行里，只能反复微调，或者干脆放弃、再点一次 tidy 把自己的编排冲掉。

卡片尺寸还按类型不同（`CARD_SIZE`：image 180×165、audio 210×125、text 200×140…），所以「看起来对齐」这件事更难靠手感做到。

## 约束

1. **网格作底，卡片对齐优先**。自由拖拽落在 `SNAP_GRID`（10）的倍数上；一旦某轴命中卡片对齐线，该轴改用对齐值。**两轴各自独立判定**——x 命中对齐、y 没命中，就是「x 用对齐值 + y 用网格值」。
2. **对齐口径 6 条线**：x 轴 left / center / right，y 轴 top / middle / bottom。同轴的三条互相组合（含 left↔right 这类贴合），不做等距分布提示。
3. **候选只取视口内的卡**。看不见的卡对齐了也无从感知，辅助线还会指向屏外。拖拽开始时快照一次视口内卡的几何，**拖拽期间不重算**——候选集固定，每帧只做比对。
4. **多选拖拽用整组包围盒**对齐选区外的卡；组内相对位置不变（与 RF 选区拖动语义一致）。
5. **阈值按屏幕像素算**：`6 / zoom` 换算成画布坐标，缩小画布时不会变得黏手。
6. **按住 Alt 全部绕过**（网格 + 对齐都关，也不画线），与 Figma / Sketch 一致。
7. **辅助线是纯瞬态**：只活在拖拽期间，不进 store 的持久化切片，不入撤销栈。吸附改变的是最终坐标，落库仍走既有 `persistDraggedNodes`（撤销、坐标回写一律不改）。
8. **纯几何下沉可单测**：候选筛选、命中判定、偏移与辅助线线段计算都是纯函数，进 `lib/`；RF 接线与渲染留在组件。
9. UI 复用既有令牌：辅助线用品牌青 `--color-teal`，1px 虚线；不新增颜色、不新增动画类。

## 成功标准

1. 自由拖一张卡松手，坐标 x / y 均为 10 的倍数（该轴未命中对齐线时）。
2. 拖动一张卡到与另一张卡左边缘相差 ≤ 6px（屏幕距离）处，卡**吸到完全对齐**，并出现一条青色虚线跨连这两张卡。
3. 六条线各自可命中：left↔left、center↔center、right↔right、top↔top、middle↔middle、bottom↔bottom。
4. 同轴同时命中多张卡时，辅助线**从最边缘的两张卡各外延 12px**（一条线串起所有对齐者），不是每对画一条。
5. 缩放到 50% 时，手感一致——仍是「屏幕上差 6px 以内就吸」，不是画布单位 6。
6. 多选三张卡一起拖，整组包围盒与选区外的卡对齐；组内三张的相对位置一字不差。
7. 按住 Alt 拖拽：不吸附、不画线，坐标可停在任意小数位。
8. 松手后辅助线立即消失；⌘Z 撤销回到拖动前坐标（既有行为不回退）。
9. 拖拽过程中不新增每帧的 store 写入——辅助线状态留在组件本地。

## 方案

RF 12 的两处事实决定了实现形态（读 `@xyflow/system@0.0.77` 源码确认）：

- **网格吸附**在 `XYDrag.updateNodes` 内完成（`index.js:2100-2107`），每帧从 store 读 `snapToGrid` / `snapGrid`。所以直接用 `<ReactFlow snapToGrid snapGrid={[10,10]}>`，Alt 绕过只需把 prop 切成 false，下一帧即生效。
- **卡片对齐**没有官方钩子，只能拦 `onNodesChange` 里 `type === 'position' && dragging` 的变更、在应用前改写 `change.position`（RF 官方 helper-lines 示例即此法）。选区拖动时一帧内有 N 条 position change，按整组包围盒算出**一个公共偏移**再逐条应用，满足约束 4。

分层：

| 文件 | 职责 |
|---|---|
| `src/lib/align-guides.ts`（新） | 纯几何：视口内候选筛选、六线命中判定、偏移与辅助线线段计算 |
| `src/components/canvas/AlignGuides.tsx`（新） | 用 `ViewportPortal` 在画布坐标系里画虚线（跟随缩放平移） |
| `src/components/canvas/AssetCanvas.tsx` | 接线：`snapToGrid` prop、`onNodesChange` 拦截、Alt 监听、辅助线本地 state |

## 明确不做

- **等距分布提示**（Figma 的双箭头）：本产品卡片排布大多由 tidy 生成，手调等距的需求弱。
- **吸附到画布网格线的可视化**（画出背景网格点阵）：`Background` 组件已有点阵，无需再叠。
- **吸附距离数值标签**：Figma 有，但那服务于像素级设计稿，这里是资产画布。
- **对齐到「组 / 框」**：等后端加分组字段后另立项。

## 真机验收（2026-08-04，dev :3010，项目 Star Whisper-v82）

用合成鼠标事件驱动真实 ReactFlow 拖拽（节点拖拽走 d3-drag 的 mouse 事件，框选走 Pane 的 pointer 事件），
读 `.react-flow__node` 的 `transform` 拿画布坐标，逐条对成功标准。

已验：

1. **网格**：拖到远离所有卡的空白处松手 → `(680, 250)`，两轴均为 10 的倍数。
2. **对齐 + 辅助线**：拖 sfx_puzzle 靠近图片行 → 落在 `y=-27.5`，卡片底边正好压上相邻卡的中线；
   同时出两条线——`align-guide-y` 在 99.5（中线），`align-guide-x` 在 1460（本卡左边 ↔ veg_jungle 右边的贴合）。
3. **落点不弹跳**：拖拽中与松手后坐标一致（`during == afterDrop == afterSync`）。
   **这一条第一次是红的**——见下「真机抓到的缺陷」。
4. **多选整组**：框选三张 terrain 卡整组下拖 → 三张同为 `dy=+223`，两两相对位移 `[-240,0] / [240,0]` 前后逐字节相同；
   组的中线吸到音频行中线。
5. **阈值按屏幕像素**：同样是「距对齐线 10 个画布单位」，zoom=1 时不吸（10px > 6px，`guides=0`，停在 250）；
   zoom≈0.435 时吸住（4.35px < 6px，raw 253 → 网格 250 → **渲染 260**）。这条是逐像素步进采样出来的，
   决定性的一行：`{px:-58, raw:253, grid:250, rendered:260}`。
6. **Alt 绕过**：按住 Alt 拖 → 无辅助线，落点 `x=200.375`（不落网格）。
7. **撤销**：吸附后的拖拽 ⌘Z 一次即回到拖动前坐标（`(200,180) → (260,260) → (200,180)`）。
8. 松手后辅助线立即消失（`guidesCleared === true`）。

**真机抓到的缺陷（已修，`56028f04`）**：松手瞬间卡片弹回几像素。
根因在 `@xyflow/system` 的两处：`getEventHandlerParams` 给 `onNodeDragStop` 的 `position` 直接取
`dragItem.position`（RF 自己那份，只过了网格吸附，不含我们在 `onNodesChange` 里做的对齐改写）；
drag end 还会再发一条 `dragging:false` 的位置变更，同样带原始坐标。
两处都会把用户眼睛看到的对齐值覆盖掉。修法：落库改从 RF store 读当前渲染坐标，
落点帧用 `applyDropOffset` 承接最后一帧的偏移。**单测结构上抓不到这个** —— 它出在 RF 内部状态与
React 状态的分叉处，只有真机能暴露。

**未验到的**：

- 密集画布下的拖拽帧率没有量化（合成事件的节奏由脚本控制，测不出真实手感）。可观察到的是 32 张卡的画布上
  逐帧比对无卡顿现象，但这不是帧率数据。
- 六条线里 `left↔left` / `right↔right` / `top↔top` / `bottom↔bottom` 的**纯边对边**命中只在单测里覆盖了；
  真机上因为所有卡都落在 10 网格上、彼此边距是 10 的倍数，边对边要么已经精确相等（delta 0，只画线不移动），
  要么差 ≥10（超阈值），实测到的都是中线与跨边组合。这是网格粒度与阈值的固有关系，不是缺陷。

**一处噪声**：`pnpm test` 首轮在 dev server + 无头 Chrome 同时跑的负载下失败一次（耗时 51s，平时 20s），
随后连续四轮全绿（234 文件 / 2507 用例）。未能定位到具体用例，按超时类偶发记录在此。
