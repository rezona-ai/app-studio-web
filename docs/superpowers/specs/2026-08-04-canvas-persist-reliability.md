# 画布落位可靠性：坐标回写不再静默 + 视口不被 agent 劫持

> 状态：设计稿 · 2026-08-04
> 关联：P2 第一组（可靠性）。P0 / P1 已全部落地，P1 只剩「框 / 分组」等后端字段。
> 同组未做：P2 的「取消生成任务」「生成前预估消耗」。**2026-08-05 后端答复更新**：取消生成
> **后端明确不做**（上游 provider 无 cancel API），前端的出口是删除生成中占位卡（会 abort 在飞请求）；
> 估价端点已提供（`POST /canvas/items/generate/estimate`），分组框端点亦已提供，两者各自单独立项。

## 目的

两件事都属于「系统悄悄不听话」，用户不会察觉，只会觉得产品不可信。

### 一、坐标回写失败是静默数据丢失

`persistAssetPosition`（`actions.ts:1094`）整段吞异常：

```ts
try {
  const item = await pgcApi.updateCanvasReference(pid, itemId, assetReference(a));
  void item;
} catch { /* 坐标回写失败不阻塞 UI */ }
```

三个调用点都走它：拖停（`AssetCanvas.tsx:651`，一次一张到 N 张）、一键整理（`actions.ts:1138`，几百张卡一个 `for` 循环全量并发）、撤销位置类操作（`index.ts:726`）。

失败时前端 store 已是新坐标、后端还是旧坐标——**用户摆好位置、刷新后全部回到原处，全程零提示**。「不阻塞 UI」是对的，「不告诉用户」不是。

整理还叠了第二个问题：120 张卡就是 120 个并发 PATCH 一次性入队。浏览器对同域 HTTP/1.1 只有 6 条连接，多出来的排队，并且和画布自己的轮询、预览图抢道——整理期间其余交互被饿住。

### 二、agent 提交生成会把视口拽走

`addGenPlaceholders`（`actions.ts:430`）在建占位卡后调 `ensureVisible(position)`，越界就 `setCenter` 平移过去。这条路径**被两种来源共用**：

- 用户在画布上自己提交生成 → 跳过去是对的（否则「创建了找不到」）。
- `registerAgentGenTask` → 由 WS 事件 `media.task_submitted` 触发，是 **agent 在对话里**提交的。用户此刻可能正在画布另一头看别的东西，视口被拽走。

重连重放时这条路径同样会重新触发。

## 约束

1. **重试只对瞬时错误**：`NETWORK` / `TIMEOUT` / 5xx 退避重试 2 次（200ms、600ms）；4xx（如 item 已删）直接放弃——重试打不通的东西只是把失败延后。
2. **一批只报一条 Toast**：拖一组 / 整理上百张卡失败时不能刷屏。短窗口（800ms）内聚合成一条「N 张卡的位置未能保存」。
3. **失败不回滚前端坐标**：卡留在用户摆的地方（回滚会让画面在用户眼前跳一下，比不保存更糟）。Toast 只做告知。
4. **整理并发上限 6**：与浏览器同域连接数对齐，整理期间轮询 / 预览图不被饿死。总耗时相近。
   ⚠️ **已被 `2026-08-05-canvas-batch-position` 取代**：后端提供批量端点后一次整理只发 **1 个**请求，
   限流闸门整段退役。本条与成功标准 4（峰值 ≤6）仅作历史记录。
5. **agent 路径不跑视口**：`ensureVisible` 只留给用户自己在画布上发起的生成。
6. **角标自愈**：提示「N 个新资产」的角标按**当前视口**实时计算——用户自己平移过去看到了，角标自动消失，不留幽灵。
7. **瞬态不落盘**：角标用的 id 列表是瞬态，不进 persist 白名单。
8. **纯逻辑下沉**：并发限流、重试判定、视口外筛选都是纯函数进 `lib/`；IO 与 DOM 留在 action / 组件。
9. UI 复用既有令牌与 `.anim-pop-in`，不新增按钮种类、不自造 toast。

## 成功标准

1. 断网后拖一张卡：坐标不回滚，重试两次后出一条 Toast 告知未保存；恢复网络再拖一次能正常保存。
2. 一批失败（拖 3 张 / 整理 120 张）只出**一条** Toast，文案含张数。
3. 4xx 失败不重试（只发 1 个请求），瞬时错误重试到第 3 次为止（共 3 个请求）。
4. 整理 120 张卡时在飞 PATCH 数**恒 ≤ 6**。
5. agent 在对话里提交生成 → 视口纹丝不动。
6. 用户在画布上双击生成 / 表单生成 → 行为与现在一致（越界仍平移带入）。
7. agent 建的卡在视口外时出现「N 个新资产 →」角标，点它飞过去并消失。
8. 用户自己平移到那张卡附近 → 角标自行消失（不需要点）。
9. 切项目 / 卡被删 → 角标不残留。

## 方案

| 文件 | 职责 |
|---|---|
| `src/lib/concurrency.ts`（新） | `createLimiter(limit)` —— **共享**闸门（初版是按批限流的 `runWithLimit`，真机量到峰值 12 后改成共享并删掉旧实现） |
| `src/lib/retry.ts`（新） | `isTransient(err)` + `retryAsync(fn, delays)` |
| `src/store/actions.ts` | `persistAssetPosition` 接重试、失败聚合、同坐标在飞合并与共享闸门；`persistAssetPositions` 收编拖拽 / 整理 / 撤销三条路径；`addGenPlaceholders` 按来源决定跑不跑视口 |
| `src/store/types.ts` | `ServerState` 加瞬态 `agentNewAssetIds: string[]`（放 ServerState 而非 UIState：`actions.ts` 只能直接 `set` 状态切片，不能经 `get()` 取 UI action，见既有 `undoStack` 同款处理） |
| `src/components/canvas/NewAssetsBadge.tsx`（新） | 订阅 `useViewport()` 自行算「还在视口外的那几个」，渲染角标；点击飞过去 |
| `src/lib/align-guides.ts` | 复用既有 `visibleRects` 做视口内判定，不再写第二套视口数学 |

角标位置定在搜索栏正下方居中（`absolute top-16 left-1/2 -translate-x-1/2 z-10`）——画布左侧是列表面板、右侧是属性面板、底部中间是工具条、底部右侧是筛选，只有这里不与既有浮层打架。

## 明确不做

- **失败卡上打「未保存」持久角标**：要给 Asset 加瞬态字段 + 一套卡上 UI，成本高一档；本轮先用 Toast 告知，看真实失败率再决定要不要升级。
- **回写失败自动回滚坐标**：见约束 3。
- **批量坐标端点**：后端没有，前端只能限流。若后端将来提供 `PATCH /canvas/items` 批量接口，闸门这层可以整段退役。
  ✅ **已发生**：后端 2026-08-05 提供该端点，闸门与 `src/lib/concurrency.ts` 已删除，见
  `2026-08-05-canvas-batch-position`。
- **取消生成任务**：2026-08-05 起记为**后端明确不做**（上游 provider 无 cancel API），不再是「等端点」。
  前端出口是删除生成中占位卡（`2026-07-22-cancel-generating-on-delete`）。
- **生成前预估消耗**：端点已于 2026-08-05 提供，单独立项。

## 真机验收（2026-08-04，dev :3010，项目 Star Whisper-v82，32 张卡）

手法：在页面里把 `window.fetch` 包一层，只掐 / 只统计坐标回写那条 `PATCH /canvas/items/{id}`，
其余请求照常；用合成鼠标事件驱动真实 ReactFlow 拖拽；状态经仓库自带的 dev 调试句柄
`window.__store`（`store/index.ts` 既有，生产构建剔除）读取。

已验：

1. **断网拖一张卡**：坐标停在用户放的地方（560,0 → 740,123，未回滚），PATCH 共 3 次（初次 + 200ms + 600ms 两次退避），
   Toast 文案 `Couldn't save the position of 1 card(s) — try moving them again` —— count 插值生效。
2. **恢复网络再拖**：1 次请求、200，正常落库。
3. **批量失败聚合**：8 张卡的选区在断网下拖动 → 24 次尝试（8 × 3），页面上只出现**一条** Toast，count 为 8。
4. **拖 32 张卡的选区**：在飞 PATCH 峰值 **6**，共 32 个请求、32 个不同 id、**0 重复**。
5. **角标**：标记两张视口外的卡 → 搜索栏正下方出现「2 new asset(s) →」；点它飞过去、角标消失、记录清空。
6. **角标自愈**：标记一张视口外的卡后**不点**角标，改由用户自己改视口让它进入视口 → 角标自行消失，
   而 store 里的 id 列表**没有**被清（`agentNewAssetIds.length === 1`）—— 正是「按当前视口实时算」的设计。

**真机抓到的两个缺陷（已修）**：

- **限流只盖住了一半**（`8d10f821`）：只给 tidy 加了限流，拖拽落库仍是 `AssetCanvas.tsx` 里逐张
  fire-and-forget 的 for 循环 —— 拖一个 32 张卡的选区照样 32 个并发。三条路径（拖拽 / 整理 / 撤销）
  统一收敛到 `persistAssetPositions`。
- **同一批坐标被写了两遍、峰值 12**（`c7a33761`）：量到 24 个 id 各 PATCH 两次（全 200）。
  原因是拖停时 RF 会连打两次回调，且两批各开各的 6 槽窗口。改为「同坐标在飞即合并」+
  所有位置回写共用**一个** `createLimiter(6)` 闸门；按批限流的 `runWithLimit` 随之退役删除（不留 dead code）。
  复测：峰值 6、32 请求、0 重复。**这两个都是单测结构上看不见的** —— 一个出在组件接线的另一条路径上，
  一个出在 RF 的回调时序里。

**未验到的**：

- **agent 真实路径**：让 agent 在对话里真提交一次生成要花积分、等分钟级，本轮按计划没做。
  角标与「不跑视口」的分支由单测覆盖（`actions.test.ts` 三条 + `NewAssetsBadge.test.tsx` 六条），
  真机验的是往 `agentNewAssetIds` 里塞 id 之后的表现，等价于该路径的下游。
- **tidy 的限流峰值**：真机上点整理时画布本来就是整齐的，只有 1 张卡需要回写（peak=1），压不出限流。
  限流本身由 `createLimiter` 单测与上面第 4 条（同一条代码路径）覆盖。

**收尾**：验收把全画布整体挪动过，最后逐张核对已还原到验收前坐标（32/32 完全一致，重载后确认为落库状态）。
过程中试图用「拖拽 + 闭环纠偏」还原时踩了一次坑：拖拽期 store 里的坐标被 `isDraggingRef` 冻结，
读它做闭环等于读旧值，循环会一路累加位移把卡甩飞（已由 ⌘Z 撤回）。要在拖拽期读位置，得读 DOM 的 transform。
